# Daily-Driver Polish — Design

**Date:** 2026-06-14
**Branch:** `dy/daily-driver-polish`
**Goal:** Remove the small frictions and trust-breakers that make Dockyard feel less than
a default daily driver. Five mostly-independent improvements, sequenced quick-wins first.

## Scope

| # | Area | Item |
|---|------|------|
| 1 | Trust | Stop `AppCommit.swift` from dirtying the working tree |
| 2 | Trust | Event-driven branch-rename sync (FSEvents on `.git/HEAD`) |
| 3 | Friction | Cmd+N goes straight to directory picker; Cmd+Shift+N to create-new |
| 4 | Polish | Sidebar declutter + density (richer rows, global PRs, recent, status strip) |
| 5 | Creative | Claude usage meter (parse local transcripts, show window consumption) |

Out of scope (explicitly declined): per-workstream model picker, git diff-stat extras
beyond a row hint, session cost-per-call display, command palette.

---

## 1. AppCommit.swift dirty state

**Problem:** `Sources/Models/AppCommit.swift` is generated by the `Generate AppCommit`
prebuild script (`project.yml:194-198`) on every build, but the file is tracked in git.
Every build rewrites the commit hash / source path / configuration, so the working tree
is permanently dirty and the file shows in every diff.

**Approach:** Treat `AppCommit.swift` as a pure build artifact — never tracked, always
generated before compile.
- `git rm --cached Sources/Models/AppCommit.swift` (stop tracking).
- Add `Sources/Models/AppCommit.swift` to `.gitignore`.
- Do **not** commit a placeholder. Instead, guarantee the file is generated before any
  target that consumes it compiles. Targets that reference it: the main app target,
  `FFRun`, and `DyAgentState`. Today only `FFRun` carries the `Generate AppCommit`
  prebuild script.
- Add the same idempotent `Generate AppCommit` prebuild step to the other consuming
  targets (the script just writes the file; safe to run N times). Verify a clean checkout
  (file absent) + `xcodegen generate` + build succeeds.

**Verification:** After a build, `git status` shows no `AppCommit.swift` entry. A fresh
clone (no `AppCommit.swift` present) builds cleanly.

**Risk:** Build-graph ordering — a consuming target could compile before the generating
target's prebuild runs. Mitigation: give each consuming target its own generation
prebuild (idempotent; just writes the file). The script is cheap and safe to run N times.

## 2. Event-driven branch-rename sync

**Problem:** Workstream names sync from their git branch only via the 15s polling timer in
`ContentView` (`syncWorkstreamNamesFromBranches()`), gated by `refreshPathValidity()`
having populated the branch-name cache. After an agent or manual `git branch -m`, the
sidebar can lag up to ~15s, which reads as flaky.

**Approach:** Add an FSEvents watcher per valid worktree on its `.git/HEAD` file, mirroring
the existing run-state FSEvents watcher pattern. On a HEAD change (debounced ~200ms):
1. Re-read that worktree's current branch (`GitOperations.repoInfo` or a lighter
   `git symbolic-ref --short HEAD`), update `branchNameCache`.
2. Run the name-sync for that worktree (extract short name after last `/`, update
   `workstream.name`, save).
3. Re-read `.dockyard-state/description` if present (so the description the agent writes
   surfaces immediately).

Keep the 15s poll as a backstop for anything the watcher misses (e.g. worktrees added
after watcher setup — re-scan watchers when projects change).

**Note on worktrees:** In a git worktree, `.git` is a file pointing at
`<main>/.git/worktrees/<name>`, and `HEAD` lives in that per-worktree dir. The watcher
must resolve the real HEAD path (read the `.git` file's `gitdir:` line, watch
`<gitdir>/HEAD`). Implementation must handle both real repos and linked worktrees.

**Verification:** Rename a branch via terminal `git branch -m`; the sidebar workstream
name updates within ~1s without waiting for the 15s tick.

## 3. Cmd+N friction

**Problem:** With no project selected, both Cmd+N and Cmd+Shift+N currently open the
`AddProjectChoiceSheet` (a two-button New/Existing chooser). The 99% case is "add an
existing folder," so the chooser is an extra click.

**Approach:**
- `.addNew` handler (Cmd+N): when nothing/no project is selected, call
  `openDirectoryPicker()` directly instead of `showingAddProjectChoice = true`.
  (Context-sensitivity unchanged: with a project/workstream selected, Cmd+N still adds a
  workstream.)
- `.addProject` handler (Cmd+Shift+N): go straight to the create-new-project sheet
  (`showingNewProjectName = true`) instead of the chooser.
- Keep `AddProjectChoiceSheet` reachable from the "+" button as a small menu
  (Add Existing… / Create New…) so both paths remain discoverable by mouse.

**Verification:** Cmd+N (no selection) opens the macOS directory picker. Cmd+Shift+N opens
the name sheet. The "+" button still offers both.

## 4. Sidebar declutter + density

**Declutter:** Remove the Recent/A-Z segmented `Picker` (`ProjectSidebar.swift:440-449`),
default sort to `.recent`. (Keep `ProjectSortOrder` enum; just stop showing the control.)

**Target layout:**

```
┌─────────────────────────────┐
│ ▾ my-project          ●3 PR │  project row + open-PR count badge
│   ● fix-login-timeout  #42  │  richer row: state dot + branch + PR
│   ◐ add-usage-meter    ±120 │  state dot (working) + dirty/diff hint
│   ○ scan-deep-thr           │  idle dot
│ ▾ Open PRs (global)         │  collapsible: all open PRs across projects
│   #42 fix-login   my-project│
│ ▾ Recent                    │  last touched, fast switching
│   add-usage-meter · 2m ago  │
├─────────────────────────────┤
│ 2 projects · 4 ws · 1 PR    │  status strip (counts)
│ ◴ 5h: ~38% left · resets 1h │  usage meter (see §5)
└─────────────────────────────┘
```

**Richer workstream rows:** Add an agent-state dot driven by the existing
`AgentStateStore` (working / waiting / idle), the branch/PR text already present, and an
optional uncommitted-changes hint (`±N` files or a dot). Reuse existing PR/branch data;
no new git calls beyond what's cached.

**Global Open PRs section:** A collapsible section listing every open PR across all
projects (PR number, title, owning project), clicking jumps to that workstream. Data comes
from the already-fetched `branchPRs` cache in `AppEnvironment`.

**Recent section:** A short collapsible "Recent" list of the last N touched workstreams
(by `lastAccessedAt`) for fast switching, independent of project grouping.

**Status strip:** A compact bottom strip showing counts (projects, workstreams, open PRs)
and hosting the usage meter line.

**Staging:** Implement incrementally and build after each piece — richer rows first
(highest daily value), then status strip + usage, then global PRs, then recent. If the
sidebar starts to feel cluttered in practice, sections are individually toggle-able /
removable; we dial back rather than ship noise.

**Localization:** All new strings (section headers "Open PRs", "Recent", status-strip
labels) added to all 5 locale files.

## 5. Claude usage meter

**Goal:** See how much Claude usage is left in the current rolling window.

**Data source:** Claude Code writes per-message records to
`~/.claude/projects/<encoded-path>/*.jsonl`. Assistant message lines contain
`"usage":{"input_tokens","output_tokens","cache_creation_input_tokens",
"cache_read_input_tokens",...}`, a `"timestamp"`, and `"model"`. This is local, requires
no API/auth, and is the same source the community `ccusage` tool uses.

**Computation:**
- Scan transcript files, parse assistant lines with `usage` + `timestamp`.
- Aggregate token totals over two windows:
  - **5-hour block:** the current rolling 5h window (Claude's short-window limit).
  - **7-day window:** rolling weekly.
- Cache results; recompute periodically (e.g. on the existing 15s timer or a dedicated
  slower timer) and on app foreground. Parsing is bounded by reading only recent files /
  tailing — only lines within the last 7 days matter, so old files can be skipped by mtime.

**Display ("remaining"):**
- Consumption (tokens used in each window) is exact and always shown.
- "Remaining %" requires a limit. Anthropic does not publish exact subscription token
  limits, so add a setting `dockyard.claudePlanTier` with cases:
  `none` (default), `pro`, `max5`, `max20`. When set, use approximate community-known
  limits to render "~N% left" + the window reset countdown. Clearly mark as approximate.
- When tier is `none`: show consumption + reset countdown only (no %).

**UI:** A single compact line in the sidebar status strip:
`◴ 5h: ~38% left · resets in 1h12m` (or `◴ 5h: 412k tok · resets in 1h12m` when no tier).
Tooltip / Settings expands detail (5h and 7d breakdown).

**New model:** `ClaudeUsage` (parser + aggregator), `ClaudeUsageStore: ObservableObject`
(published windows), settings key `dockyard.claudePlanTier`.

**Verification:** With recent Claude Code activity, the meter shows non-zero consumption
and a sensible reset countdown; changing plan tier in Settings updates the % readout.

**Risk / honesty:** The % is approximate by nature. The reset-window boundaries and limit
constants may drift as Anthropic changes plans; keep the limit constants in one place and
labelled clearly. The feature degrades gracefully to consumption-only.
